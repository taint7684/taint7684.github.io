Context

Enterprise groups with many legal entities must register every employee for compulsory social, health and unemployment insurance, report monthly changes to the social insurance agency and withhold personal income tax correctly. The rules change often, depend on dates, and differ by contract type, nationality and region.

The client was replacing a legacy HR system. The new platform had to keep what the legacy system did right, fix what it did wrong, and follow the latest regulations.

Method: one pipeline from requirement to task

Each function moves through the same sequence. A problem found lower down is fixed at the highest affected document and then flows back down, so documents never contradict each other.

  1. Requirement reviewRead the client's requirement document against regulations and legacy behaviour. Log every contradiction, gap and copy error with an ID, then record the client's decision.
  2. Confirmed requirementsProduce a clean, frozen version in the client's own language — no user stories or technical terms.
  3. Functional specification (FSD)Field-level screens and behaviour, a clickable mockup, business rules in EARS form, acceptance criteria, message and event codes from a shared catalogue, import/export templates.
  4. Front-end and back-end handoffWhat each side must do — screens, routes, endpoints, permissions, errors, data needs — without prescribing how to code it.
  5. Test scenariosAcceptance test cases with a matrix from every acceptance criterion and business rule to at least one test.
  6. Task breakdownDeveloper tasks ordered by dependency, each traced back to its story and criteria.

Rule examples (from public regulations)

Written in EARS form so developers and QA read the same sentence. Figures are illustrative and follow public law, not client data.

RuleWhy it matters
WHEN the contribution salary exceeds 20 × the statutory reference (base) salary, THE SYSTEM SHALL cap social and health insurance contributions at that ceiling.Over-deduction from employees is a compliance and trust issue.
WHEN the contribution salary is below the regional minimum wage for the employee's work location, THE SYSTEM SHALL warn the user before saving.Region comes from the organisation module, so the rule depends on correct master data.
WHEN a contribution rate or wage parameter changes, THE SYSTEM SHALL store it as a new effective-dated record and propose closing the previous one.Past payrolls must recalculate with the rates that applied at the time.
WHEN a parameter record has already been used in a calculation, THE SYSTEM SHALL block deletion and allow only an end date.Protects audit history.
WHEN a user records an insurance book transaction, THE SYSTEM SHALL enforce the order collect → close → hand over to the employee.Prevents handing back a book that was never closed.
WHEN two policy settings match the same employee, THE SYSTEM SHALL apply the one with the narrower scope (legal entity over company-wide).Groups need one default policy with local exceptions.

Quality controls

Consistency checks

Cross-checked FSDs, workflows and test scenarios so a rule, its screen and its test always say the same thing. Open questions are marked in place as [NEEDS CLARIFICATION: …] and collected in one list for the client.

Responsible AI use

Used ChatGPT and Claude to draft FSD sections, test scenarios and meeting summaries. Every output was checked against the source documents and confirmed rules before it entered a specification.

What I learned

  • Effective dates are the hardest part of payroll-related rules. Nearly every parameter needs a start and end date, and every calculation must pick the version valid on its own date.
  • The legacy system is evidence, not the specification. It shows real usage, but it also carries old mistakes; each behaviour has to be checked against the current law.
  • Map the whole flow first. Writing functions one by one hides dependencies between modules; a single end-to-end map makes them visible early.
