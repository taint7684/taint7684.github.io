Social Insurance & PIT: turning regulations into testable specifications

Two modules of an enterprise HRM platform, where every number on a payslip or a declaration depends on rules that change with time, contract type, nationality and region.

Role
Business Analyst
Company
FPT IS
Modules
Social Insurance · Personal Income Tax
Also supported
Payroll · Attendance

Problem

Insurance and tax rules are date-dependent, vary by employee and change often. Legacy system behaviour had to be checked against updated requirements before anything was built.

Approach

Map the module end to end, review requirements for gaps and contradictions, then specify every function at field level with explicit business rules and acceptance criteria.

Delivered Delivered

50+ functions specified through FSDs and mockups, with use cases, user stories, test cases and user manuals.

01 · Problem

Rules that change with time and with each employee

Groups with many legal entities must register every employee for compulsory social, health and unemployment insurance, report monthly changes to the social insurance agency and withhold personal income tax correctly. The rules depend on effective dates and differ by contract type, nationality and region.

If a rule is vague in the specification, it becomes a calculation error in production: an employee over- or under-deducted, or a declaration rejected by the agency.

Business objectives

  • Give developers rules precise enough to implement without guessing.
  • Give QA a test for every rule, so compliance can be proven before release.
  • Resolve gaps and contradictions with stakeholders before development, not after.
02 · Analysis

One end-to-end map before any single function

I mapped the module as one flow first, so each specification knows where its data comes from and where it goes.

What the analysis covered

  • Regulations: translated regulatory requirements into calculation logic and validation conditions.
  • Legacy behaviour: compared how the legacy system worked with the updated requirements, and logged functional gaps, inconsistencies and unclear rules.
  • Stakeholders: clarified every open item before development, and worked with developers and QA through testing.
03 · Requirements

Rules written so developers and QA read the same sentence

Business rules follow the EARS pattern. The examples below are written from public law only; figures are illustrative.

RuleWhy it matters
WHEN the contribution salary exceeds 20 × the statutory reference salary, THE SYSTEM SHALL cap social and health insurance contributions at that ceiling.Over-deduction is a compliance and trust issue.
WHEN the contribution salary is below the regional minimum wage for the work location, THE SYSTEM SHALL warn the user before saving.The region comes from organisation data, so the rule depends on correct master data.
WHEN a contribution rate or wage parameter changes, THE SYSTEM SHALL store it as a new effective-dated record and propose closing the previous one.Past periods must recalculate with the rates that applied at the time.
WHEN a parameter record has already been used in a calculation, THE SYSTEM SHALL block deletion and allow only an end date.Protects the audit trail.
WHEN two policy settings match the same employee, THE SYSTEM SHALL apply the one with the narrower scope.Groups need one default policy with local exceptions.
04 · Specification

One pipeline from requirement to task

Each function moves through the same sequence. A problem found lower down is fixed in the highest affected document and then flows back down, so documents never contradict each other.

  1. Requirement reviewRead the requirement document against regulations and legacy behaviour; log every contradiction, gap and copy error, and record the decision.
  2. Confirmed requirementsA clean, agreed version in the client's own language.
  3. Functional specificationField-level screens and behaviour, mockups, business rules, acceptance criteria and import/export templates.
  4. Front-end and back-end handoffWhat each side must deliver — screens, endpoints, permissions, errors and data needs — without prescribing how to code it.
  5. Test scenariosAcceptance tests mapped from every acceptance criterion and business rule.

Deliverables

  • FSDs with mockups for 50+ functions
  • Business rules, calculation logic and validations
  • Use cases and user stories
  • Test cases and test scenarios
  • User manuals
  • Gap and open-question list from the legacy and requirement review
05 · Validation

Consistency is checked, not assumed

Cross-checks

FSDs, workflows and test scenarios are cross-checked so a rule, its screen and its test always say the same thing. Open questions are marked in place and collected in one list for stakeholders.

AI with verification

I use ChatGPT and Claude to draft FSD sections, test scenarios and meeting summaries. Every output is checked against source documents and confirmed rules before it enters a specification.

06 · Takeaways

What this case shows

  • Effective dates are the hardest part of payroll rules. Nearly every parameter needs a start and end date, and every calculation must pick the version valid on its own date.
  • A legacy system is evidence, not the specification. It shows real usage but can also carry old mistakes; each behaviour is checked against current law.
  • Map the whole flow first. Writing functions one by one hides dependencies between modules; one end-to-end map makes them visible early.
